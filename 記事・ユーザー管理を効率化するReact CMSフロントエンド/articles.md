# 記事・ユーザー管理を効率化する React CMS フロントエンドを作りました

## はじめに

フェンリル株式会社のインターンシップ 2026 で、フロントエンドチームに参加しました。

私は三田学園高等学校 1 年生の田中博悠です。  
普段の個人開発では React などのフロントエンドに触ることも多いですが、どちらかというとバックエンドの方が好きです。

フロントエンドが苦手というわけではないものの、得意と言い切れるほどでもありません。  
特にデザイン面は AI にかなり任せてしまうことも多く、バックエンドのように自分の手でゴリゴリ書けている感覚はあまりありませんでした。

それでもフロントエンドコースを選んだのは、フェンリルのサイトで「未経験者が Kotlin / Jetpack Compose 開発に挑戦」というインターン記事を見て、自分もフロントエンドに挑戦してみてもよいのではないかと思ったからです。

今回のインターンでは、**React SPA + TanStack Router** を使って、SNS 管理者向け CMS のフロントエンドを開発しました。

5 日間という短い期間でしたが、実装そのものだけでなく、レビューを通して「管理画面をどう作るか」「どこに責務を置くか」をかなり考える機会になりました。

## 作ったもの

今回作ったのは、SNS 管理者が記事やユーザーを管理するための CMS フロントエンドです。

主に実装した画面は以下です。

- 記事一覧
- 記事詳細
- ユーザー一覧
- ユーザー詳細

記事一覧では、検索・ソート・ページネーションを使って大量の投稿を扱いやすくしました。  
また、リスト表示とカード表示を切り替えられるようにして、記事の状態や投稿日時、いいね数などを確認しやすくしました。

ユーザー側では、ユーザー一覧・詳細画面を作り、ユーザーの状態確認や凍結 / 解除、投稿記事の確認ができるようにしました。

## 技術構成

主に使った技術は以下です。

- React
- TypeScript
- TanStack Router
- Tailwind CSS
- axios

CSS や UI コンポーネントの設計は、仕様を満たせるなら比較的自由に選べる形だったので、私は Tailwind CSS を使って実装しました。

Tailwind CSS は `className` が長くなりがちな弱点はありますが、短期間で画面を組むうえではかなり速く、今回のようなインターン開発では相性がよかったです。

## 画面より先に、扱いやすい設計を作る

今回の実装で特に意識したのは、画面側に処理を書きすぎないことです。

管理画面は、似たような一覧画面や詳細画面が多くなります。  
そのため、毎回 API 呼び出しやソート処理、UI 部品を画面ごとに書いていると、すぐに見通しが悪くなります。

そこで、以下のように責務を分けることを意識しました。

- API 呼び出しは CMS クライアントに寄せる
- データ取得は TanStack Router の loader に寄せる
- ソート処理は hooks に分ける
- Pagination や SearchInput などは共通コンポーネントにする

## API 呼び出しを CMS クライアントに寄せる

API を呼び出す処理は、画面から直接 axios を書くのではなく、`cms` というクライアント経由で呼べるようにしました。

イメージとしては、以下のように呼び出せる形です。

```ts
await cms.auth.login({ email, password });
await cms.articles.getArticles();
await cms.users.getUser(userId);
```

実装では、`Cms` クラスの中に `auth`、`users`、`admins`、`articles` を持たせています。

```ts
export class Cms {
  readonly auth = new AuthApi();
  readonly users = new UsersApi();
  readonly admins = new AdminsApi();
  readonly articles = new ArticlesApi();
}

export const cms = new Cms();
```

こうしておくと、画面側では「どのエンドポイントにどんな axios 設定で投げるか」をあまり意識せず、`cms.articles.getArticles()` のように目的ベースで API を呼べます。

また、axios の共通設定ではトークン付与やエラー変換もまとめました。

```ts
cmsClient.interceptors.request.use((config) => {
  const token = getStoredToken();
  if (token) {
    config.headers.set("X-PecoriToken", token);
  }
  return config;
});
```

認証トークンの付与を共通化しておくことで、各 API 呼び出しで毎回ヘッダーを意識せずに済みます。

## TanStack Router の loader を使う

記事一覧では、ページ表示前に TanStack Router の `loader` で記事データを取得するようにしました。

```ts
export const Route = createFileRoute("/articles/")({
  component: () => <Article />,
  loader: async () => {
    try {
      const response = await cms.articles.getArticles();
      return response.articles;
    } catch (error) {
      if (error instanceof CmsApiError && error.status === 401) {
        clearStoredToken();
        localStorage.removeItem("admin");
        throw redirect({ to: "/login" });
      }

      throw error;
    }
  },
  pendingComponent: () => <Loading />,
});
```

最初は `useEffect` でデータ取得を書くことも考えていました。  
ただ、PR レビューで「URL から取得対象が明らかなデータは TanStack Router の loader で取得するのがよい」と指摘してもらい、ページ表示に必要なデータは loader に寄せる形に直しました。

`useEffect` は便利ですが、何でも入れてしまうと「いつ、何が起きるのか」が追いにくくなります。  
今回の実装では、ページに必要な初期データ取得は loader、画面内の表示状態は React の state、というように分ける意識ができました。

## ソート処理を hooks に分ける

記事一覧やユーザー一覧では、複数の条件で並び替えができるようにしました。

記事では例えば以下のようなソートがあります。

- 投稿 ID
- ユーザー ID
- ニックネーム
- いいね数
- 投稿日時
- 公開状態

これらを画面コンポーネントの中に全部書くと、JSX とロジックが混ざって読みづらくなります。  
そこで、記事用には `useArticleSort`、ユーザー用には `useUserSort` を作り、ソート処理を分離しました。

```ts
const { sortedArticles } = useArticleSort(
  data instanceof CmsApiError ? [] : data,
  sort,
);
```

内部では `useMemo` を使い、元の配列をコピーしてからソートしています。

```ts
const sortedArticles = useMemo(() => {
  return [...articles].sort((a, b) => {
    switch (sortOption) {
      case "good-up":
        return compare(a.good, b.good);
      case "good-down":
        return compare(b.good, a.good);
      case "date-up":
        return new Date(a.postedAt).getTime() - new Date(b.postedAt).getTime();
      case "date-down":
        return new Date(b.postedAt).getTime() - new Date(a.postedAt).getTime();
      default:
        return 0;
    }
  });
}, [articles, sortOption]);
```

このように分けることで、画面側は「どのソートを選んでいるか」と「ソート済みのデータを表示すること」に集中できます。

## 共通コンポーネント化したもの

管理画面では、似た UI が何度も出てきます。

今回、特に共通化を意識したのは以下です。

- `Pagination`
- `SearchInput`
- `SortDropdown`
- `Button`

記事一覧とユーザー一覧は、扱うデータこそ違いますが、検索・ソート・ページネーションという構造はかなり似ています。

そのため、一覧画面ごとに UI を作り直すのではなく、共通コンポーネントとして切り出して使い回せるようにしました。

短期間の開発では、とにかく目の前の画面を完成させたくなります。  
ただ、同じような画面が複数あるときは、最初に少しだけ共通化を意識しておくと、後から直しやすくなると感じました。

## よくできたこと

今回よくできたと思うのは、処理を役割ごとに分けて、画面側を薄くできたことです。

特に以下は、自分の中でも成長を感じました。

- API 呼び出しを `libs/cms` に分けたこと
- ソート処理を hooks に分けたこと
- 共通 UI をコンポーネント化したこと
- TanStack Router の loader の使い方を理解できたこと

最初は「動けばいい」という気持ちで進めそうになりましたが、レビューをもらいながら「あとから読む人が分かりやすいか」「画面に責務が集まりすぎていないか」を考えるようになりました。

## あと一歩だったこと

一番大きな反省点は git 操作です。

適当な場所からブランチを切りすぎて、push 時にコンフリクトが多発しました。  
その結果、一日をほぼコンフリクト解消作業に費やしてしまいました。

PR レビューでも、ログイン画面の PR にその先の画面実装まで混ざってしまっていたため、そろそろ PR を分割した方がよさそうだとコメントをもらいました。  
これは、自分のブランチ運用が整理できていなかったことが原因だと思います。

コードを書く前に、どのブランチから作業を始めるのかを確認するべきでした。  
また、作業を小さく commit して、早めに pull / rebase しておけば、ここまで大きく詰まらなかったと思います。

もう一つの反省点は、事前調査です。

OpenAPI から自力で API クライアントを書いたのですが、あとから OpenAPI generator があることを知りました。  
もちろん自分で書いたことで API クライアントの構造は理解できましたが、短期間の開発では「既に使えるツールがないか」を先に調べるべきでした。

「調べればよかった……」という感じです。

## レビューで学んだこと

今回のインターンでは、PR レビューでかなり具体的な指摘をもらいました。

特に印象に残っているのは、ライブラリの使い方だけでなく、責務の置き方やユーザーの使いやすさまで見てもらえたことです。

ここでは、自分が実際に PR レビューで指摘してもらった内容を中心に振り返ります。

### useEffect ではなく loader に寄せる

記事一覧のデータ取得を `useEffect` で行う実装にしていたところ、レビューで「エッジケースを考えると面倒になりがちなので、取得対象が URL から明らかなら TanStack Router の loader がよい」と指摘されました。

この指摘で、単にデータが取れればよいのではなく、ページに必要なデータ取得をルーター側に寄せることで、コンポーネント側の責務を減らせると理解しました。

### 認証エラーだけを見てログインへ戻す

認証チェックの処理では、最初は API 呼び出しでエラーが出たらトークンを消してログイン画面へ戻すような実装にしていました。

しかしレビューで、サーバーや CDN の一時的な不調、クライアントのオフラインなど、トークンに問題がない場合でも再ログインが必要になってしまうと指摘されました。  
そのため、エラー内容を見て、本当に 401 の認証エラーだった場合だけトークンを削除するように意識しました。

これは、エラーハンドリングを「失敗したから全部ログアウト」ではなく、失敗の種類ごとに分けて考える必要があると学んだポイントです。

### トークン保存は置き場所だけで終わらない

認証トークンの保存についてもレビューでコメントをもらいました。

最初は localStorage に保存すること自体をどう扱うかに意識が向いていましたが、レビューでは HTTP-only Cookie を使えない SPA の事情や、localStorage を使う場合は CSP なども含めて考える必要があると教えてもらいました。

セキュリティは「どこに保存するか」だけで終わる話ではなく、アプリ全体としてどう守るかを考える必要があると感じました。

### label と input の紐づけ

ログイン画面では、`label` と入力欄が紐づいていないという指摘もありました。

見た目だけならラベルは表示されていますが、`label` に `htmlFor` を指定して `input` の `id` と紐づける、または `label` の中に `input` を含めることで、アクセシビリティやクリック時の挙動が良くなります。

また、入力欄に `id` や `name` を付けると、ブラウザのオートコンプリートが効きやすくなることも教えてもらいました。  
UI は見た目だけでなく、ブラウザや支援技術にとって扱いやすいマークアップにする必要があると感じました。

### 環境変数と Vite の作法

API の URL をハードコーディングしていた部分には、`.env` に置く方が望ましいという指摘をもらいました。

また、Vite では `.env` をコミットしてよく、秘匿情報は `.env.local` に置くというプラクティスも教えてもらいました。  
それまで `.env` は基本的にコミットしないものだと思っていたので、Vite の作法として理解できたのは大きかったです。

### useMemo はいつでも使えばよいわけではない

ログイン画面で、エラーがあるかどうかの判定に `useMemo` を使っていたところ、処理が軽いのであえて `useMemo` しなくてもよいとコメントをもらいました。

`useMemo` は最適化のために使うものですが、軽い処理に使うと、むしろオーバーヘッドやコードの複雑さの方が大きくなる場合があります。  
React の API を知っているだけでなく、使うべき場面かどうかを判断することが大切だと学びました。

### API クライアントにも設計の余地がある

CMS クライアントについては、自分ではかなり整理できたと思っていました。  
ただ、レビューでは、各 API メソッドに似たような `try/catch` が増えているので、エラー変換は共通の wrapper に寄せられそうだと指摘してもらいました。

また、型定義をすべて `types` に集めるのではなく、責務ごとに近い場所へ置く選択肢や、状態を持たない class にする意味があるかどうかもコメントしてもらいました。

このあたりは、単に「動く API クライアント」を作るだけでなく、後から機能が増えたときにどう保守しやすくするかを考えるきっかけになりました。

### 細かい命名や整形も読みやすさにつながる

ソートの値に `up` / `down` を使っていたところ、`ascending` / `descending` の方が意味が明確だとコメントをもらいました。

また、クラス名の合成には `clsx` のようなライブラリを使うと読みやすくなること、Prettier や Biome などで整形するとインデントや空行が揃うことも指摘されました。

どれも単体では小さな指摘ですが、コードを読む人にとっての分かりやすさに効いてくる部分だと思いました。

## AI との向き合い方

今回の開発を振り返ると、最近の私はフロントエンド開発で AI に頼りすぎていたと感じました。

AI を使うこと自体は悪いことではないと思います。  
ただ、自分で設計や実装を説明できないまま進めてしまうと、レビューで指摘をもらったときに理解が追いつかなくなります。

これからは AI を使いつつも、最終的には自分で読める、自分で書ける、自分で説明できる状態を目指したいです。

特にフロントエンドでは、UI の構造、状態管理、データ取得、副作用の置き場所など、自分で判断できるように練習していきたいです。

## まとめ

5 日間で SNS 管理者向け CMS のフロントエンドを作りながら、React の書き方だけでなく、管理画面を作る考え方まで学べました。

短期間の開発だったので、できたことも反省点もかなりはっきり出ました。

よくできたことは、処理を分けて画面を薄くし、共通化を意識できたことです。  
あと一歩だったことは、git 操作と事前調査です。

次に開発するときは、コードを書く前にブランチの切り方と使えるツールを確認し、AI に頼るだけでなく、自分でも書けるように練習していきます。

レビューや相談に付き合ってくださったメンターの方々、本当にありがとうございました。
