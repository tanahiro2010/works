# Hono Conference 2026 Proposal Talk Flow

## タイトル

**果たして本当に、Honoはバックエンドフレームワークなりや？**

### 副題

**Honoをフルスタックフレームワークとしてみた時のベストプラクティス**

---

## 1. 導入：Honoってバックエンドフレームワークですよね？

まずは一般的なHonoのイメージから入る。

```text
Hono
= 軽量
= Web API
= バックエンド
```

しかし実際には、

- JSXが書ける
- HTMLを返せる
- formを受けられる
- Cookieを扱える
- DBにアクセスできる
- SSRできる

つまり、

> 「……これ、普通にWebアプリ全部作れるのでは？」

という疑問が生まれる。

ここでタイトルを回収する。

> **果たして本当に、Honoはバックエンドフレームワークなりや？**

---

## 2. 実は昔からこの作り方はある

ここでPHPを出す。

PHPはJavaScriptなしでもWebアプリを作れる。

```text
GET
↓
PHP
↓
DB
↓
HTML
```

フォーム送信も、

```text
POST
↓
DB更新
↓
Redirect
↓
GET
```

で成立する。

Honoも同じような構造を作れる。

```text
GET
↓
Hono
↓
DB
↓
JSX
↓
HTML
```

ここでの主張：

> Honoが新しいのではなく、
> 昔からあるシンプルなWeb開発を
> モダンなJavaScript環境で再現できる。

---

## 3. じゃあ、なぜ今それをやるのか

モダンなフレームワークは便利だが、機能が多い。

React / Next.jsなどを使うと、初心者はいきなり以下の概念に遭遇する。

- state
- effect
- hydration
- Server / Client境界
- API
- fetch
- cache
- 再レンダリング
- フォーム状態
- 非同期処理

作りたいものとは直接関係のない設計判断が大量に発生する。

例えば、

> Todoアプリを作りたいだけなのに、
> Webアーキテクチャの博士課程が始まる。

という状態になりがち。

ここでの問い：

> **必要になる前から、複雑さを導入しすぎているのでは？**

---

## 4. Honoだけで作ると何が単純になるのか

小説投稿サイトを具体例にする。

### React / クライアントフェッチ中心

```text
Browser
↓
JavaScript起動
↓
fetch
↓
API
↓
DB
↓
JSON
↓
state更新
↓
render
```

場合によってはさらにAPI内部から外部APIへアクセスする。

### Hono SSR

```text
Browser
↓
Hono
↓
DB
↓
HTML
```

投稿処理も、

```text
<form>
↓
POST
↓
DB
↓
Redirect
↓
GET
```

で済む。

### 実体験

以前、

- Next.jsで小説投稿サイトを作った
- Honoオンリーでも小説投稿サイトを作ろうとした

という経験があり、後者の方が体感でも明らかに処理が速かった。

ただし、

> 「Next.jsそのものが遅い」

という話ではない。

重要なのは、

> **Hono SSRでは処理経路を短くしやすい**

という点。

---

## 5. 初心者だけの話ではない

この構成は初心者向けの簡易構成としてだけではなく、
要件によっては経験者にとっても合理的。

特に、

- 小説投稿サイト
- ブログ
- 管理画面
- CRUD中心のSaaS
- 社内ツール
- フォーム中心のサービス
- DBの読み書きが中心のWebアプリ

などは、複雑なクライアント状態を持たないことが多い。

つまり、

> **複雑なクライアント状態を必要としないなら、
> そもそもクライアントアプリケーションを作る必要がない。**

---

## 6. Honoをフルスタックで使う時のベストプラクティス

副題の本題。

基本方針は、

> **Server First / JavaScript on Demand**

### Level 1

```text
Hono
+
SSR
+
HTML Form
```

まずはこれだけで作る。

### Level 2

必要な箇所だけClient JavaScriptを追加する。

例：

- モーダル
- プレビュー
- 部分更新
- 軽いインタラクション

### Level 3

クライアント状態が本当に複雑になったらReactなどを導入する。

```text
Hono + SSR + Form
↓
必要な箇所だけClient JS
↓
必要ならReactなどを導入
```

重要なのは、

> **Reactを使わないことではない。**
>
> **Reactを使う理由が生まれるまで使わないこと。**

---

## 7. 「でも、あとで困らない？」

ここで最大の反論を扱う。

> 最初からNext.jsなどで、
> フロントとバックエンドをちゃんと分離しておいた方がよくない？

Honoの場合、ビジネスロジックを分離しておけば、
あとから比較的簡単にAPI化できる。

```text
Route
↓
Service
↓
Repository / DB
```

例えば最初は、

```tsx
app.get('/novels/:id', async (c) => {
  const novel = await novelService.find(c.req.param('id'))

  return c.html(
    <NovelPage novel={novel} />
  )
})
```

あとから、

```tsx
app.get('/api/novels/:id', async (c) => {
  const novel = await novelService.find(c.req.param('id'))

  return c.json(novel)
})
```

のように変更できる。

もちろん実際には、

- 認証
- CSRF
- API仕様
- エラー形式

などの調整は必要。

しかし、コアロジックを再利用しやすい。

ここでの主張：

> **Honoでフルスタックを始めることは、
> フルスタックに縛られることではない。**

---

## 8. むしろ最初から複雑にすると戻しにくい

Next.jsなどのモダンなフルスタックフレームワークに深く依存すると、

- routing
- data fetching
- server action
- cache
- rendering
- client/server境界

などがフレームワークの設計と密結合しやすい。

あとからフレームワークを変更しようとすると、
画面だけではなくデータ取得やレンダリング方式まで変更する必要が出る。

一方、HonoをシンプルなSSRとして始めれば、
後から必要な部分だけ分離しやすい。

ここでの主張：

> **拡張可能であることと、
> 最初から拡張後の姿で作ることは違う。**

さらに、

> **将来必要になるかもしれない複雑さを、
> 現在のコードに前払いしない。**

という設計思想につなげる。

---

## 9. どこまでHonoだけでやるべきか

Honoオンリーが向いているケースと、
クライアントフレームワークを導入した方がいいケースを整理する。

### Honoオンリーが向いていそう

- CRUD
- DB読み書き中心
- 管理画面
- ブログ
- 小説投稿
- フォーム主体
- コンテンツ表示主体
- 比較的単純なSaaS

### Reactなどを導入した方がよさそう

- リアルタイム共同編集
- ドラッグ&ドロップ主体
- 複雑なClient State
- オフライン対応
- Figmaのような高度なUI
- Notionのような高い操作性が必要なUI

つまり、

> **クライアントJSを使わないこと自体を目的にしない。**

---

## 10. 結論

最後は3段階で問いを回収する。

### Honoはバックエンドフレームワークなのか？

**Yes.**

### Honoはフルスタックフレームワークとして使えるのか？

**Yes.**

### ではReactはいらないのか？

**必要になったら使えばいい。**

締めの候補：

> **Reactを使わないのではない。**
>
> **Reactを使う理由が生まれるまで、使わない。**

または、

> **必要になるまで、複雑さを導入しない。**

---

# トーク全体の核

このトークは単なる

> 「Honoはフルスタックでも使えます」

という機能紹介ではない。

Honoを通して、

- Webアプリに本当にクライアントアプリケーションは必要なのか
- モダンなWeb開発は複雑さを前払いしすぎていないか
- 最小構成から始めることは本当に悪いことなのか
- 将来の拡張性と現在の単純さは両立できるのか

を考える。

最終的な思想は、

> **複雑さは必要になってから導入する。**

そしてHonoは、そのための選択肢としてかなり相性が良い。
