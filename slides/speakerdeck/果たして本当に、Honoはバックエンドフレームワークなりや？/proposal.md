# Hono Conference 2026 Proposal

## タイトル

個人開発者よ、Honoを使え

## サブタイトル

複雑さを前払いしないWebアプリ設計

## 概要

個人開発でWebアプリを作ろうとすると、気づけば最初からReactやNext.jsを前提にしていることがあります。もちろん、それらが必要な場面は多くあります。アニメーションが多いポートフォリオ、複雑な状態を持つ管理画面、Slackのような高機能チャット、リッチな編集体験を持つアプリケーションでは、ReactやNext.jsは強力な選択肢です。

しかし、すべての個人開発がそこから始まる必要はあるのでしょうか。

小さなポートフォリオ、ブログ、投稿サービス、管理画面、フォーム中心のWebアプリ、簡単なチャットなどでは、必要なものは意外と単純です。HTMLを返す、フォームを受ける、DBを読む、リダイレクトする、必要な場所だけJavaScriptを足す。それだけで十分なケースは少なくありません。

本セッションでは、登壇者が個人開発として作っている小説投稿サイトを題材にします。Next.jsで小説投稿サイトを作った経験と、Honoだけで同種のアプリケーションを組もうとした経験を比較しながら、「Honoで十分なもの」と「ReactやNext.jsを使うべきもの」の境界を整理します。Honoを単なるAPIサーバー用フレームワークとしてではなく、Webアプリケーションを小さく始めるための中核として使う設計パターンを紹介します。

主張は「Reactを使うな」でも「Next.jsを使うな」でもありません。

Reactを使う理由が生まれるまで、Reactを使わない。Next.jsが必要になる理由があるなら使う。そうでないなら、Hono + SSR + HTML Form + 必要なJavaScriptで、まず完成まで走れる構成を選ぶ。

個人開発において、完成までの摩擦を減らすことは重要な設計判断です。このトークでは、そのためのHono活用パターンを具体例とともに話します。

## 想定する内容

### 1. 個人開発、気づいたら重くなりがち問題

個人開発でWebアプリを作るとき、最初に技術選定が膨らみがちです。

- Reactを使うか
- Next.jsを使うか
- APIを分けるか
- クライアント状態をどう持つか
- fetch/cache/hydrationをどう考えるか
- WebSocketをReactのライフサイクルにどう載せるか
- フォーム状態やエラー表示をどう管理するか

本当は「投稿できる」「読める」「送れる」「表示できる」を作りたいだけなのに、先にフロントエンドアーキテクチャの複雑さを背負ってしまうことがあります。

### 2. 作りたい体験から技術を選ぶ

いくつかの例を使って、Hono / React / Next.js の使い分けを考えます。

- アニメーションが多いポートフォリオにReact: わかる
- アニメーションが多いだけのポートフォリオにNext.js: 本当に必要か考えたい
- アニメーションが少ないポートフォリオにReact: なしではない
- アニメーションがないポートフォリオにReact: まずHonoでよくないか
- ただのチャットにReact: WebSocketのライフサイクル管理が主役になりすぎるかもしれない
- SlackのようなチャットにReact: わかる
- CRUD中心の投稿サービスにSPA: 本当にクライアント状態が主役か考えたい
- 管理画面にHono SSR: かなり相性がいい

技術選定を「流行」ではなく、「UIの複雑さ」「クライアント状態の量」「サーバー状態の扱い方」から考えます。

### 3. Honoで十分なケースの構造

登壇者の個人開発である小説投稿サイトでは、基本的な画面の多くが「一覧を見る」「作品を読む」「投稿する」「編集する」「コメントする」といった、サーバー状態を中心とした処理でした。

Next.jsで作ったときは、画面、API、fetch、JSON、state更新、再レンダリングなど、1つの機能を作るために考える経路が自然と長くなりました。一方で、Honoだけで同種の構成を試すと、一覧や詳細、投稿処理のような基本機能はかなり短い経路で表現できました。

HonoでWebアプリを作ると、処理経路を短くできます。

```text
GET
↓
Hono
↓
DB
↓
JSX
↓
HTML
```

フォーム投稿も、昔ながらのPost/Redirect/Getで扱えます。

```text
POST
↓
DB更新
↓
Redirect
↓
GET
```

クライアント中心の構成で必要になりがちな、fetch、JSON、state更新、再レンダリング、フォーム状態管理などを、最初からすべて導入しなくて済みます。

小説投稿サイトのように、ユーザー体験の中心が「読む」「投稿する」「編集する」である場合、最初からクライアントアプリケーションとして作り込むより、Hono SSRでサーバー状態を素直にHTMLへ落とす方が自然な場面があります。

### 4. Hono + JavaScript on Demand

基本方針は、Server First / JavaScript on Demand です。

```text
Level 1:
Hono + SSR + HTML Form

Level 2:
必要なところだけVanilla JS

Level 3:
複雑なUIだけReactなどを導入

Level 4:
必要ならAPI化・フロントエンド分離
```

たとえば簡単なチャットなら、HonoでWebSocketを受け、クライアントは少しのJavaScriptで `send` と `message` を扱うだけで成立します。一方で、スレッド、リアクション、未読管理、リッチエディタ、複数ペイン、複雑なローカル状態が必要になったらReactを導入する理由があります。

重要なのは、最初から最大構成を選ぶのではなく、必要になった複雑さだけを足していくことです。

### 5. Honoで始めても、後で詰まない設計

HonoでSSRから始める場合でも、Routeにすべてを書き込むのではなく、ビジネスロジックを分けておくことで後からAPI化しやすくなります。

```text
Route
↓
Service
↓
Repository / DB
```

たとえば最初はHTMLを返します。

```tsx
app.get('/novels/:id', async (c) => {
  const novel = await novelService.find(c.req.param('id'))

  return c.html(
    <NovelPage novel={novel} />
  )
})
```

必要になれば、同じServiceを使ってJSON APIも作れます。

```tsx
app.get('/api/novels/:id', async (c) => {
  const novel = await novelService.find(c.req.param('id'))

  return c.json(novel)
})
```

Honoで小さく始めることは、将来の拡張性を捨てることではありません。

### 6. 持ち帰れる判断基準

セッションでは、参加者が自分の開発に持ち帰れる判断基準を整理します。

Honoで始めやすいもの:

- ポートフォリオ
- ブログ
- 小説投稿サイトのような投稿サービス
- フォーム中心のサービス
- CRUD中心のSaaS
- 管理画面
- 社内ツール
- 軽量なチャット

Reactを導入したくなるもの:

- 複雑なClient Stateを持つ画面
- 画面全体が頻繁に変化するUI
- ドラッグ&ドロップ中心のUI
- リアルタイムに複数箇所が同期するUI
- リッチエディタ
- SlackやNotionのような操作体験

Next.jsを選ぶ理由になりやすいもの:

- Reactを前提にした大きめのアプリケーション
- SSG/ISRが強く効くサイト
- App Router/RSCを活かしたい設計
- 画像最適化などNext.jsの機能が明確に必要なサイト
- Vercel中心の運用体験を選びたい場合

## 参加者が得られるもの

- HonoをAPIサーバー以外の用途で使う具体的な考え方
- Hono SSR / HTML Form / Vanilla JSを組み合わせる設計パターン
- 個人開発でReactやNext.jsを導入する前に確認する判断基準
- Honoで小さく始め、必要に応じてReactやAPI分離へ進む段階的な拡張方針
- Route / Service / Repository に分けることで、SSRとAPIを両立しやすくする実装方針

## このトークの独自性

このトークは、Honoの基本的な入門解説ではありません。

登壇者自身が、個人開発として小説投稿サイトを作っている中で、Next.jsを使った実装と、Honoだけで同種のアプリケーションを作ろうとした実装を比較した経験を出発点にしています。その中で感じた「処理経路の短さ」「実装時に考えることの少なさ」「完成までの摩擦の差」を、Honoの設計パターンとして整理します。

小説投稿サイトは、単なるTodoアプリよりも現実的な題材です。一覧、詳細、投稿、編集、認証、コメント、いいね、管理画面など、個人開発として十分に実用的な機能を持ちながら、必ずしも高度なクライアント状態を必要としません。この題材を通して、Hono SSRがどこまで実戦投入できるのか、どこからReactやNext.jsが欲しくなるのかを具体的に話します。

また、ReactやNext.jsを否定するのではなく、ポートフォリオ、チャット、ブログ、投稿サービス、管理画面といった複数の例を通して、Honoで十分なケースと、React / Next.jsを選ぶべきケースを具体的に切り分けます。

Honoコミュニティに対しては、「Honoはバックエンドフレームワークか？」という問いを少しずらして、「Honoは個人開発の複雑さをどこまで減らせるか？」という視点を提示します。

## 想定聴講者

- HonoをAPIサーバー用途で使ったことがある人
- 個人開発でReactやNext.jsを選びがちな人
- 小さなWebアプリをもっと軽く作りたい人
- SSR / HTML Form / Vanilla JSの構成を現代のTypeScript環境で見直したい人
- HonoをフルスタックWebアプリの中核として使う設計に興味がある人

## まとめ

個人開発者よ、Honoを使え。

それは、Honoだけを使えという意味ではありません。Reactを捨てろという意味でも、Next.jsを敵にしろという意味でもありません。

Honoで十分なものまで、最初から重くしなくていい。HTMLで返せるものはHTMLで返し、Formで済むものはFormで済ませ、必要なところだけJavaScriptを足す。ReactやNext.jsは、それを使う理由が生まれたときに呼べばいい。

複雑さは、必要になってから導入する。

Honoは、そのための個人開発にちょうどいい土台です。
