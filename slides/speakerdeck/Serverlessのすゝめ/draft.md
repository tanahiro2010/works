- Serverlessとは
  - Serverlessとは、サーバーの管理（バージョン管理やネットワークの設定など）を意識せずにアプリケーションを開発・運用できるクラウドコンピューティングのモデルです。
  - 代表的なサービスとしてAWS Lambda、Google Cloud Functions、Azure Functionsなどがあります。
  - Serverlessの利点として、スケーラビリティの自動化、コスト効率の向上、開発速度の向上などが挙げられます。

- オンプレとは
  - オンプレミス（オンプレ）とは、企業や組織が自社のデータセンターやサーバーを所有・運用する形態のことを指します。
  - オンプレの利点として、データの完全なコントロール、カスタマイズ性の高さ、セキュリティの強化などが挙げられます。
  - しかし、初期投資が高額であり、スケーラビリティの確保が難しいという欠点もあります。
  - ここでいうオンプレは企業ではなく自宅のサーバーを指します

  - セキュリティとかネットワークとか怖くないの？
- 問いかけへの答え

- 比較観点の紹介
  1. コスト
  2. スケーラビリティ(と言っても個人の趣味レベルでの話)
  3. セキュリティ
  4. 運用の難易度
  5. 開発のしやすさ
- マシンの紹介
  - 自宅鯖のスペック
    - CPU: Xeon E3-1200 v2
    - メモリ: 32GB
    - ストレージ: SSD 1TB + HDD いっぱい
    - OS: Ubuntu Server 20.04
  - Serverlessのスペック
    - Vercelの無料枠を使用
    - Neonの無料枠を使用
    - Superbaseの無料枠を使用
  - コストはなるべくどちらも無料に収まるように設定
- 実例紹介：やすみ？
  - 実際に自分が運用しているサービス「やすみ？」を例に、Serverlessとオンプレの違いを見ていく
  - 「やすみ？」はDocker上で動作している
  - サーバー自体は自分で管理しているため、Serverlessとは違ってインフラ部分も自分で面倒を見る必要がある
- CI/CD
  - オンプレでCI/CD環境を整えるのはかなり面倒
  - GitHub ActionsのSelf-hosted Runnerを使ってデプロイしている
  - Runnerの導入
  - 権限設定
  - Dockerを操作できるようにする
  - Secretsの管理
  - Runner自体の死活管理
  - デプロイスクリプトの作成
  - 一度作れば便利だが、そこまでの「路線を引く」のが大変
  - ServerlessではGitHub連携などでかなり簡単にCI/CDを構築できるサービスも多い
  - Serverlessの良さは、CI/CDそのものより「自分で管理するレイヤーが少ない」こと

- サーバーの再起動
  - オンプレではOSアップデートなどでサーバーを再起動する必要がある
  - 再起動すると当然、そのサーバー上のサービスも一時的に止まる
  - Dockerコンテナが正常に再起動するか確認
  - Cloudflaredが正常に起動するか確認
  - DBが正常に起動するか確認
  - ダウンタイムがどれくらい発生したか確認
  - 「再起動するだけ」でも考えることが多い
  - これを何らかで自動化することもできるんだろうけど、やっぱり面倒
  - ServerlessではOSや物理サーバーの再起動を基本的に利用者が意識しなくてよい

- Serverlessとは何だったのか
  - Serverlessは「サーバーが存在しない」という意味ではない
  - サーバーは当然どこかに存在している
  - ただし、OS・ネットワーク・再起動・ハードウェアなどを利用者が意識する必要が少ない
  - Serverless = サーバーについて考える範囲を減らせる仕組み

- コスト
  - Serverlessは小規模であれば無料枠で運用できることも多い
  - 使用量に応じた課金モデルが多い
  - オンプレではサーバー本体・ストレージ・電気代などが必要
  - ハードウェア故障時には交換費用も発生する
  - ちなみに自分のサーバーは学校に置いているので電気代は払っていない
  - そのため自分は電気代についてはあまり詳しくない
  - ※オンプレの電気代が無料という意味ではない

- オンプレの強み：自由度
  - Serverlessには実行時間・ランタイム・ストレージなどの制約がある
  - オンプレではOSレベルで自由に操作できる
  - SSHで直接サーバーに入れる
  - 好きなソフトウェアをインストールできる
  - PostgreSQL、Redisなどを自由に立てられる
  - 常駐プロセスを自由に動かせる
  - Dockerも自由に利用できる
    - ServerlessでDockerを使えるサービスを僕はみたことがないので、これはかなり大きな強みだと思う
  - OSやネットワークそのものを触ることができる

- SSHの魅力
  - SSHでサーバーに入り、その場で状態を確認できる
  - docker ps
  - htop
  - journalctl
  - psql
  - ログを直接見る
  - 設定ファイルを直接変更する
  - Serverlessでは触れないような低いレイヤーまで操作できる
    - 実際、オンプレだとVercel的なサービスを作れるが、VercelでVercelを作ることはできない。できたとしてもとても面倒
  - サーバーそのものを触る楽しさがある

- Docker + Cloudflared
  - CloudflaredをDockerコンテナとして動かすことができる
  - 各DockerコンテナをCloudflare Tunnel経由で外部公開できる
  - ルーター側で大量にポートを開放しなくてもサービスを公開できる
  - 例
    - app1.example.com → app1:3000
    - app2.example.com → app2:8080
    - api.example.com → api:4000
  - CPU・RAM・ストレージ・回線が許す限り、1台のサーバーに多数のサービスをホストできる
  - 個人開発では「とりあえずこのサーバーに載せる」ができるのはかなり便利
  - 性能が許せば、ほぼ無限にサイトを生やせる感覚がある

- ただし1台に集約するデメリット
  - サーバーが落ちると、そのサーバー上のサービスがまとめて落ちる
  - 再起動時も複数サービスがまとめて停止する
  - CPUやRAMをサービス同士で取り合う
  - 障害の影響範囲が大きくなりやすい
  - 自由度が高い分、構成を考える必要がある

- Serverlessの自由
  - インフラを管理しなくてよい
  - OSを管理しなくてよい
  - ハードウェアを管理しなくてよい
  - スケーリングを任せられる
  - 再起動を意識しなくてよい
  - 「管理から自由になれる」

- オンプレの自由
  - OSを自由に触れる
  - 好きなソフトを入れられる
  - 好きな構成を作れる
  - Dockerコンテナを好きなだけ立てられる
  - SSHで何でも触れる
  - 「制約から自由になれる」

- Serverlessとオンプレの違い
  - Serverless
    - アプリケーションを作ることに集中できる
    - インフラ管理をクラウド側に任せられる
    - デプロイやスケールが楽
    - ただし実行環境には制約がある
  - オンプレ
    - インフラも含めて自分で管理できる
    - 自由度が非常に高い
    - 好きなものを好きなだけ動かせる
    - ただし全部自分で面倒を見る必要がある

- Serverlessは万能ではない
  - Serverlessが向いているもの
    - Web API
    - Webアプリケーション
    - Bot
    - Cron処理
    - 小〜中規模のバックエンド
    - アクセス量が読めないサービス
  - オンプレ / VPSが向いているもの
    - 長時間実行する処理
    - 常駐プロセス
    - 重い動画処理
    - 大容量ストレージ
    - 特殊なミドルウェアが必要なもの
    - OSやネットワークを自由に触りたい場合

- 実際に両方使って思ったこと
  - サービスを作りたいだけならServerlessはかなり楽
  - オンプレを実際に運用すると、Serverlessがどれだけ面倒を肩代わりしているのかよく分かる
  - CI/CD
  - 再起動
  - OSアップデート
  - ネットワーク
  - Docker
  - DB
  - ログ
  - 障害対応
  - Serverlessではこれらの多くを考えなくてもサービスを公開できる

- それでもオンプレを使う理由
  - SSHで何でも触れる
  - Dockerを好きに使える
  - サービスを大量に載せられる
  - 自分で構成を考えられる
  - サーバーそのものを触る勉強になる
  - そして何より、ロマンがある
    - セキュリティとか完全無視していい世界なら僕は顧客情報を持ちたい（）

- 最近のクラウド移行の風潮
  - Serverlessでは、サービスが落ちても「クラウド側の責任」となることが多い
  - オンプレでは、サービスが落ちたら「自分の責任」となる
  - そして情報漏洩などが起きた場合、その会社がオンプレで運用していた場合、責任はその会社にある
    - Serverlessでは、サービスが落ちても一部クラウド側に責任を負わせることができる
  - 最近のクラウド移行の風潮は、責任をクラウド側に押し付けることができるという点で、企業にとってはメリットがあるのではないかなと

- 結論
  - Serverlessは「管理からの自由」
  - オンプレは「制約からの自由」
  - アプリケーションを作りたいならServerlessはかなりおすすめ
  - サーバーそのものを触りたいならオンプレはかなり楽しい
