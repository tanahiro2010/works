# PHPカンファレンス登壇プロポーザル

## タイトル

PHPの命名規則、結局camelCaseとsnake_caseどっちなんだ

## サブタイトル

PHPの歴史から、関数名とメソッド名の住み分けを考える

## セッション時間

40分

## セッション種別

トーク

## 想定レベル

初級から中級

PHPをある程度書いたことがあり、標準関数、クラス、メソッド、フレームワークのコードを読んだ経験がある人を想定しています。

## 概要

PHPを書いていると、標準関数には `str_replace` や `array_map` のような `snake_case` が多く見えます。一方で、現代的なフレームワークやライブラリのコードでは `$request->getParsedBody()` や `$repository->findById()` のような `camelCase` のメソッドをよく見ます。

では、PHPでは `camelCase` と `snake_case` のどちらを使うべきなのでしょうか。

このセッションでは、単純に「どちらが正しいか」を決めるのではなく、PHPの歴史をたどりながら、なぜ名前の規約が層によって分かれて見えるのかを考えます。PHPの初期、標準関数の文化、PEAR、PHP 5以降のOOP、フレームワーク文化、PHP-FIG、PSR-1までを順に見ていき、最後に現代の実装判断へ落とし込みます。

結論としては、普通の関数やヘルパー関数は `snake_case`、クラスのメソッドは `camelCase` がPHPの歴史に沿った自然な落としどころではないか、という話をします。ただし、既存プロジェクトの規約、フレームワークの規約、公開APIの互換性はそれより優先されます。

## 詳細説明

PHPの命名規則は、言語仕様として一枚岩に決まっているようには見えません。標準関数には `snake_case` が多く、PSR-1ではメソッド名に `camelCase` が定められています。さらにPEARの規約、各フレームワークの文化、PSRの立ち位置を見ていくと、「PHPではこの命名が正解」と一言でまとめるのが難しいことが分かります。

この発表では、命名規則を好みや宗教論争として扱うのではなく、「どの層の名前なのか」という観点で整理します。

- PHP標準関数に近い層
- PEARのような共有ライブラリの層
- PHP 5以降に広がったOOPとフレームワークの層
- PHP-FIGとPSRが扱った相互運用の層
- 現代のプロジェクトで実装判断する層

特にPHP-FIGとPSRについては、PHP本体の公式仕様ではない一方で、PHPエコシステムでは事実上の標準として強い存在であることを説明します。また、PSR-1のMeta DocumentではEditorとしてPaul M. Jonesが記録されていることにも触れ、FIG周辺のフレームワーク/ライブラリ文化とPSR-1の命名規則がどう接続して見えるのかを考えます。

なお、「PSR-1がなぜメソッド名にcamelCaseを選んだのか」については、現時点で決定理由を明確に説明する一次資料を見つけられていません。そのため、この部分は断言ではなく、当時のOOP PHP文化、フレームワークの命名傾向、PHP-FIG周辺の文脈からの考察として扱います。

少しくだけて言えば、「これ、当時の会議室、もうだいぶcamelCaseの香りだったんじゃね？」という仮説です。ただし、話の主軸はあくまでPHPの歴史から命名規則の住み分けを理解することです。

## 40分の構成案

1. 導入: PHP、結局どっちなん問題
2. 1995年頃: PHPの始まりと標準関数の文化
3. PHP 3以降: 拡張される言語と増える関数
4. PEAR: 初期の共有ライブラリ規約
5. PHP 5: OOPの本格化とメソッドを書くPHP
6. 2000年代後半: フレームワーク文化とcamelCaseメソッド
7. PHP-FIG: 相互運用のために集まったフレームワーク開発者たち
8. PSR-1: PHP-FIGが作った規格と命名規則
9. 現代の判断: 関数はsnake_case、メソッドはcamelCase。ただし既存規約優先
10. まとめ: 年表で振り返るPHP命名規則の層

## このセッションで持ち帰れること

- PHPの標準関数に `snake_case` が多い理由を歴史の文脈で説明できる
- PSR-1がメソッド名に `camelCase` を定めていることを理解できる
- PSRがPHP本体の仕様ではなく、PHP-FIGによるエコシステム上の規格であることを整理できる
- 「普通の関数」と「クラスのメソッド」で命名判断を分ける理由を説明できる
- 既存プロジェクト規約、フレームワーク規約、公開API互換性を優先する判断軸を持てる
