- PHPの命名規則の現状に関して改めて
  - 改めて、PHPの命名規則の現状を整理する
    - LaravelなどのフレームワークはcamelCaseを採用している
    - PHPの標準関数にはsnake_caseが多く見られるが、命名規則は一貫していない
      - ちなみに、WordPressもsnake_caseを採用中
  - 「つまり、PHPの命名規則は一貫性がない...？」
- そういうわけでもない
  - 現在、PHPの命名規則を定義した標準が存在する
    - PSR-1: Basic Coding Standard
      - 2012年6月5日にリリース
      - PHP-FIG（PHP Framework Interoperability Group / PHPフレームワーク相互運用性グループ）によって企画・作成
      - クラス名は `StudlyCaps`（PascalCase）
      - メソッド名は `camelCase`
      - クラス定数は `UPPER_CASE_WITH_UNDERSCORES`
      - プロパティ名については特定の命名規則を定めていない
        - `camelCase` / `snake_case` など、採用した規則を一貫して使うことを推奨
    - PSR-12: Extended Coding Style
      - PSR-1を前提として、より詳細なコーディングスタイルを規定
      - インデント、改行、クラス・メソッド宣言、制御構文などを詳細に定める
      - 「変数名はcamelCase」と新たに規定しているわけではない
    - ソース：https://www.php-fig.org/psr/psr-1/
- このPSR-1の規定に従うと、クラス名はStudlyCaps、メソッド名はcamelCase、クラス定数はUPPER_CASE_WITH_UNDERSCORESとなる。
- 「じゃあなんでPHPの標準はそれに従ってないねん」
  - ぶっちゃけ従ってないのには至極当然な理由がある
    - PHPの標準関数は、PHPがまだ若かりし頃に作られたものが多く、当時は命名規則の統一がされていなかった
    - そのため、snake_caseが多く採用されている
    - しかしPSR規定ができたのは2010年以降であり、PHPの標準関数の多くはそれ以前に作られたものが多い
    - そのため、PHPの標準関数はPSR規定に従っていない
  - 僕としては...
    - 「PHPができた後に規定ができたんでしょ？　なら後からできたPSR規定はなんでPHPの標準関数に従ってないんだ」
      - 読みにくいし、初心者が混乱するし、実際に僕も混乱した
      - 至極当然の疑問
- どうしてPSR規定はPHP標準関数に従っていないのか
  - PSR-1規定の冒頭で、一番最初に、目的がこう定義されている。
    - 「共有されるPHPコード間で高い技術的相互運用性を確保するため」
    - つまり、PSR規定はPHPの標準関数に従うことを目的としていない
  - そして...
    - PSR-1の規定目的がPHPの標準関数に従うことが目的とされいなかったとしても、何か理由がないとPSR規定がPHPの標準関数に従わないのはおかしい
    - 僕が調べた限り、明示的に記されていたわけではないけれど
      - おそらく、従わない理由として「そのPSR-1規定作成チームが立ち上げられた時、多分すでに著名なフレームワークが存在していて、それはキャメルケースで書かれていた」というのがあるかもしれない
        - PSR-1の作成チーム「PHP-FIG」は、2009年の php|tek で複数のフレームワーク開発者によって始まった組織
        - 2009年前後でよく使われていたPHPフレームワークはCakePHP、Symfony、Zend FrameworkやCodeIgniterなど
          - それらの命名規則は...
            - CakePHP: camelCase（ローワーキャメルケース）
            - Symfony: camelCase（ローワーキャメルケース）
            - Zend Framework: camelCase（ローワーキャメルケース）
            - CodeIgniter: snake_case
          - CodeIgniter以外はキャメルケースを採用していた
        - これから考えるに、状況証拠としてはおそらく十分
        - また、その時の創設メンバーを調べてみる
          - Zend Framework：Matthew Weier O'Phinney 氏
            - Zend Frameworkは前述通りキャメルケースを採用していた
          - Symfony：Fabien Potencier 氏
            - Symfonyも前述通りキャメルケースを採用していた
          - Doctrine：Jonathan Wage 氏
            - Doctrineもキャメルケースを採用していた
          - Solar：Paul M. Jones 氏
            - Solarもキャメルケースを採用していた
          - Lithium：Nate Abele 氏
            - Lithiumもキャメルケースを採用していた
        - ...これは、もう十分に状況証拠としては十分すぎるほど
        - つまり、PSR-1規定はPHPの標準関数に従わない理由として、当時の著名なフレームワークがキャメルケースを採用していたから、というのが十分に考えられる
          - そして創設メンバーが担当していたフレームワークは全てキャメルケースを採用していたことからもしかしたら当人たちがキャメルケースが好きだったのかもしれない（）
  - 一次資料を見つけることができなかたため、あくまで推測でしかないけれど
    - 少なくとも、PSR-1規定が何も理由なしにキャメルケースを採用したわけではないことは確か
- 余談だけど...
  - 実は、PSR以前のSymfonyにも同じ問題があった
    - Symfony 1.4では基本的にcamelCaseが使われていた
    - しかしhelper関数はunderscore形式
    - Symfony公式ドキュメント自身が
      - 「なぜhelperだけcamelCaseじゃないの？」
      - という疑問を取り上げている
    - その回答
      - helperは関数だから
      - PHPのcore functionに合わせた
    - つまり当時すでに
      - PHP標準関数の文化
      - OOPフレームワークの文化
      - の2つが共存していた
- 話の順番とか投げ打って、さらに遡る
  - そもそも、PHPの標準関数はどうしてsnake_caseが多いに関わらず、ちゃんと定まっていないのか
    - そもそもPHPは「言語設計」から始まってないから
      - PHPは、Rasmus Lerdorf氏が自分の個人用ホームページを作るために作った「Personal Home Page Tools」が始まり（1995年）
        - アクセス追跡などのためのツール群から始まり、要求に応じて機能が追加されていき…
        - その後、PHP/FI（Personal Home Page / Forms Interpreter）として発展
        - その後、PHP 3として正式にリリースされる - 1998年6月6日
      - ちょっとした個人用のツール群から始まったので、言語設計がしっかりしていなかった
        - `strpos`や`str_replace`、`htmlspecialchars`などの関数は、Rasmus Lerdorf氏が個人用のツール群として作ったもの
          - ちなみに...
            - さらに遡ると、PHPの標準関数はC言語で書かれている
              - C言語の命名規則はsnake_caseが多い
              - そのため、PHPの標準関数もsnake_caseが多い
            - つまり、PHPの標準関数はC言語の命名規則に従っている
            - そして、C言語の命名規則はsnake_caseが多い
            - つまり、PHPの標準関数はsnake_caseが多い????
        - エンジニア的に言うと「最初から30年後の巨大な言語エコシステムを想定して、API命名規則を綺麗に設計していたわけではない」
        - イメージ的には「可読性とかAPI設計とか一貫性とか、そう言うの完全度外視で作ってた個人用エコシステムがどうしてかめちゃデカシステムになってしまった」って感じ
        - というか、企業のシステムで長期的な運用を想定して開発されたシステムだって技術的負債が募るのに、個人用のツール群から始まったPHPが技術的負債を残さないわけがないというか...（個人の感想）
      - そのため、PHPの標準関数は命名規則が統一されていない
        - そして、PHPの標準関数は、Rasmus Lerdorf氏が作ったものだけでなく、他の開発者が作ったものも多く含まれている
  - しかし一応、PSR以前にも共通規約は存在した
    - その名も「PEAR 1.0」
      - PHPの拡張リポジトリ/パッケージマネージャ
      - 2002年12月27日にリリース
      - 作ったのはStig Bakkenらを中心とするPHP開発グループ
      - PEARはPSRより前からPHPライブラリ向けのコーディング規約を定めていた
        - クラス名: キャメルケース
        - メソッド名: 小文字で始めるキャメルケース
        - 変数名: キャメルケースまたは小文字のアンダースコア区切りを使う（キャメルケーススネークケースどちらでもよい）
        - グローバル変数はプレフィックスをつける
        - 定数: アッパースネークケース
      - これによって`Net_HTTP_Client`的なunderscore文化が形成された
  - そして時は進み、PHP 5がリリースされる（2004年7月13日）
    - PHP 5の主要な変更として、Zend Engine 2.0と新しいオブジェクトモデルの導入がある
      - それ以前は`mysql_query`や`array_map`のような関数ベースのAPIが主流だった
      - しかし、PHP 5からはオブジェクト指向プログラミング（OOP）が導入され、クラスやメソッドが使えるようになった
        - こんなやつ：`$request->getParsedBody()` / `$response->getStatusCode()` / `$userRepository->findById($id}`
      - ここからオブジェクト指向PHPが重要になっていく
        - この変化を経て、PHPが「関数を大量に呼ぶ言語」から、「クラス・メソッドを大量に書く言語」へ変化していった
  - 時は進み、2000年代後半
    - 話は戻り、camelCase文化がフレームワーク側で成熟していった...と言うこと！
    - 2009年にPHP-FIGが登場が登場し、あとは先ほど話した通り
- ここから読み取れることとして...
  - 「PSRがcamelCaseをPHPに持ち込んだ」ではなく、「2000年代に既に成熟していたOOP PHPのcamelCase文化を、PSRが共通規格として固定した」と言うこと
