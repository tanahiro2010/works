## 1. 先に結論

### 雛形
- スライドの「先に私の結論」パートに対応
- 記事では結論をさらに明確に文章化し、例外条件もセットで出す

### 書く内容（箇条書き）
- 結論を先出しする
  - 普通の関数（グローバル関数・ヘルパー関数・手続き的API）は `snake_case`
  - クラスのメソッドは `camelCase`
  - これは「絶対ルール」ではなく、歴史をたどった上での自然な落としどころという位置づけ
- 例外・優先順位も同時に提示（後の章で詳しく扱う予告として軽く触れる）
  - 既存プロジェクトの規約がある場合はそちらを優先
  - フレームワーク規約（Laravel, Symfony, WordPressなど）がある場合はそちらを優先
  - 公開APIの命名は互換性を壊さないことを最優先
- 記事の読み方を示す
  - 「なぜこの結論に至ったか」を歴史パートで説明していく、という導線
- 技術要素として追加できるもの
  - PSRはあくまで「コーディングスタイル規約」であり言語仕様（構文・実行時動作）ではない、という前提を先に一言入れておく
    - 変数名や関数名を間違えてもPHPの構文エラーにはならない、実行できてしまう、という技術的事実
  - この「実行できてしまう」という性質が、後の「それでも命名で悶える」章に効いてくることを伏線として書いてもよい

## 2. PHP標準関数はなぜsnake_caseっぽく見えるのか

### 雛形
- スライドの「1995 PHPが生まれる」章全体（Personal Home Page Tools〜標準機能にもcamelCaseはある、まで）に対応
- 記事ではここに技術的補足（C言語との関係、命名規則の言語比較）を追加して厚くする

### 書く内容（箇条書き）
- PHPの出自
  - Rasmus Lerdorf氏が1995年に公開した「Personal Home Page Tools（PHP Tools）」が起点
  - 元々は自分のオンライン履歴書へのアクセス追跡のためのCGIバイナリ群
  - Cで書かれていた
  - 出典: https://www.php.net/history.php.php
- 「言語」ではなく「ツール群」だったという性質
  - 要求に応じて機能が継ぎ足されていった
  - 最初から言語仕様やAPI設計方針を固めてから作られたわけではない
  - 「30年後の巨大エコシステムを想定して命名規則を整えていたわけではない」という表現で断言を避ける
- ここで生まれた関数文化
  - 文字列処理、配列操作、ファイル操作、DB接続など、Webでよく使う処理をどんどん関数として追加
  - 具体例: `str_replace`, `array_map`, `json_encode`, `file_get_contents`, `mb_strlen`, `mysqli_connect`
  - スライドと共通の例に加え、記事では追加でもう数個出してもよい（例: `array_filter`, `preg_match`, `htmlspecialchars`）
- **技術的深掘り①: なぜC言語由来だとsnake_caseになりやすいのか**
  - PHPの内部実装（Zend Engine含む）はCで書かれている
  - C言語の標準ライブラリ（libcなど）の命名は伝統的にlowercase + underscore（例: `strcpy`, `memcpy`, `time`）
  - PHPの初期のビルトイン関数はCの関数を薄くラップする形で作られたものが多く、Cの命名文化がそのまま引き継がれた面がある
  - ただし「PHPの標準関数はC言語の命名規則にただ従っているだけ」と単純化しすぎない注意書きを入れる（一次資料で全関数を検証したわけではないため）
- 完全に統一されているわけではないという注意
  - 「PHP標準関数 = すべてsnake_case」ではない
  - 標準クラスのメソップ側にはcamelCase/PascalCase系がある
    - `ReflectionClass::getName()`
    - `ReflectionMethod::getParameters()`
    - `DateTime::setTimezone()`
  - ここは「グローバル関数の文化」と「標準クラス/メソッドの文化」を分けて見る必要がある、という整理をはっきり書く
- **技術的深掘り②: PHP公式マニュアルにあるuserland naming rules**
  - 出典: https://www.php.net/manual/en/userlandnaming.rules.php
  - 関数名: 単語間にアンダースコアを使う、という方針が明記されている
  - クラス名: camelCaseとPascalCaseの両方が使われている
  - `strpos()` が過去の命名ミスの例として公式マニュアル内で言及されている点は面白ネタとして使える
    - （本来 `str_pos` になるべきところがなっていない、という有名な不整合）
  - `DOMDocument`, `SplFileObject` など、標準クラス側はcamelCase/PascalCase系の名前になっている
- この章のまとめ的一文（記事の骨格として）
  - 「PHPの標準関数がsnake_caseに見えるのは、言語設計の結果というより、Cベースの実装文化がそのまま持ち込まれた結果に近い」という見立てを提示

## 3. PHP 3で広がる関数ベースのWeb言語

### 雛形
- スライドの「1998 PHP 3リリース」章に対応
- スライドでは3枚程度だが、記事では歴史的経緯＋技術的な「なぜ後から直せないのか」を厚めに書く

### 書く内容（箇条書き）
- PHP 3の位置づけ
  - PHP/FIからPHPへの大きな節目
  - 1998年6月に公式な後継としてリリース
  - 出典: https://www.php.net/history.php.php
- 開発体制の変化
  - 個人開発から、複数の開発者が関わる体制に拡大
  - モジュール（拡張）という形で機能が足されていく仕組みが整い始める
- 「機能拡張と実用が先、命名の一貫性は後回し」という視点
  - Web開発の実用上の要求（DB接続、フォーム処理、セッションなど）に応じて関数がどんどん追加された
  - この時点でAPIレビューや命名ガイドラインのような統制機構は存在しなかった
- **技術的深掘り: 一度公開されたAPIの命名を変えるコスト**
  - 後方互換性（BC: Backward Compatibility）という概念を導入して説明する
  - 関数名を変更する/別名にすると、既存の膨大なコードベース（当時からすでにWeb上で使われ始めていた）が壊れる
  - PHPが「後方互換性を重視する言語」として知られていく背景の一つとしてここで触れてもよい
  - 具体例として、後年 `mysql_*` 系関数が非推奨化→削除されるまでに10年以上かかったことなどを軽く触れると、命名や設計の変更がいかに困難かの実例になる（要出典確認、日付はメモ程度に留める）
- 命名は「設計思想」だけでは決まらないという整理
  - 「いつ作られたか」「誰が作ったか」「どの文化圏から来たか」「互換性を壊せるか」「どの層のAPIか」という軸を提示
  - これはスライドの「命名は設計思想だけでは決まらない」パートに対応するので、記事ではこの軸それぞれに簡単な具体例を1つずつ添える
    - いつ: 2000年以前 vs PSR以降
    - 誰が: Rasmus Lerdorf氏個人 vs PHP-FIGのようなグループ
    - 文化圏: C言語文化 vs OOPフレームワーク文化
    - 互換性: グローバル関数（互換性維持コスト大）vs 新規フレームワークのAPI（維持コスト小）
    - 層: 言語組み込み関数 vs ユーザーランドのクラス

## 4. PSR以前のPEAR規約

### 雛形
- スライドの「2002 PEAR規約が登場」章に対応
- 記事ではPEARの規約を表だけでなく、原文に近いニュアンスで補足する

### 書く内容（箇条書き）
- PEARの位置づけ
  - PHP Extension and Application Repository
  - 2002年12月27日リリース（要出典再確認、Stig Bakkenらが中心）
  - PHPの拡張・パッケージ配布システムとして機能
- PEARの命名規約（出典: https://pear.php.net/manual/en/standards.naming.php）
  - クラス名: 先頭大文字、階層をアンダースコアで表現
    - 例: `Log`, `Net_Finger`, `HTML_Upload_Error`
  - クラス変数・メソッド: studly caps / camel caps
    - 例: `$counter`, `connect()`, `getData()`, `buildSomeWidget()`
  - 定数: 大文字とアンダースコア（アッパースネークケース）
  - グローバル変数にはプレフィックスをつける慣習
- PEARが面白いポイント（記事オリジナルの解説を厚めに）
  - クラス名の `_` 区切りは「名前空間がなかった時代の疑似名前空間」として機能していたという技術的背景
    - PHPに名前空間（`namespace`）が入るのはPHP 5.3（2009年）
    - それ以前はクラス名の衝突を避けるために `Net_Finger` のようなプレフィックス的な命名で疑似的に階層を表現していた
    - これは今のnamespace `Net\Finger` に相当する役割を、命名規則だけで代替していたと説明できる
  - メソッド名・グローバル関数の命名にcamel系を推奨していた点
    - PHP標準関数のsnake_case文化とは別の系統の規約がすでにこの時期に存在していたことを示す
    - 「関数=snake_case」という単純な図式ではないことの証拠として使う
- ここでの整理
  - 「標準関数の層」と「ライブラリ配布の層」はそもそも別の文化圏だったという整理をはっきり書く
  - 記事の結論（普通の関数はsnake_case）は、PEAR規約から導かれたものではなく、あくまでPHP標準関数文化＋現代の文脈からの判断であることを明記する（読者に誤解させないための重要な線引き）

## 5. PHP 5でOOP PHPが強くなる

### 雛形
- スライドの「2004 PHP 5リリース」章に対応
- 記事ではZend Engine 2.0の技術的な変更点をもう一段掘り下げる

### 書く内容（箇条書き）
- PHP 5の基本情報
  - 2004年7月13日リリース
  - Zend Engine 2.0の導入
  - 出典: https://www.php.net/history.php.php
- Zend Engine 2.0がもたらした変更（技術的深掘り）
  - オブジェクトが「値」ではなく「ハンドル（参照）」として扱われるようになった
    - PHP 4まではオブジェクトの受け渡しでコピーが発生し、OOPとして扱いにくかった
    - PHP 5でオブジェクトの受け渡しがハンドル経由になり、他言語のOOPに近い挙動になった
  - `private` / `protected` / `public` といったアクセス修飾子の導入
  - インターフェース（`interface`）、抽象クラス（`abstract class`）の導入
  - `__construct` / `__destruct` などのマジックメソッドの整理
  - これらにより「まともにクラス設計ができる言語」になったことが、OOP文化がPHPで本格的に育つ土台になった、という説明をする
- 関数ベースからメソッドベースへ
  - Before: `array_map($callback, $items)`
  - After: `$request->getParsedBody()`
  - この変化がコードの見た目だけでなく、設計思想の変化（手続き的→オブジェクト指向）でもあることを書く
- メソッド名の例をスライドより増やす
  - `getParsedBody()`, `getStatusCode()`, `findById()`, `setCreatedAt()`, `hasPermission()`, `isPublished()`
  - それぞれ簡単に「Getter」「Setter」「述語（is/has）」のような命名パターンの分類として紹介してもよい
    - get/set/is/has接頭辞はJavaのBeansの命名規則にも近く、他言語のOOP命名文化からの影響を軽く触れてもよい（要出典確認、あくまで一般論として）
- ここでの結論的一文
  - PHP 5によってはじめて「メソッドという単位で命名を考える文化」がPHPに根付き始めた、という位置づけ

## 6. 2000年代後半のフレームワーク文化

### 雛形
- スライドの「フレームワーク文化」〜「しょうもない仮説」章に対応
- 記事では一次資料の限界を明記しつつ、状況証拠の並べ方を丁寧に文章化する

### 書く内容（箇条書き）
- 登場したフレームワーク/ライブラリ
  - CakePHP, Symfony, Zend Framework, CodeIgniter, Doctrine
  - それぞれのメソッド命名の傾向（記事内表として整理）
    - CakePHP: camelCase
    - Symfony: camelCase
    - Zend Framework: camelCase
    - Doctrine: camelCase
    - CodeIgniter: snake_case寄り（例外として明記）
- ここは断言を避けるという方針を明記
  - 「PSR-1がcamelCaseを選んだ理由」の一次資料はまだ見つかっていないことを正直に書く

- 仮説の提示（記事のノリとして少し緩めてもいいパート）
  - 「PSRが後からcamelCaseを持ち込んだ」のではなく「すでに広がっていたOOP文化をPSRが追認・固定した」と見る方が自然、という仮説
  - この仮説を支える状況証拠を列挙
    - 2009年時点で主要フレームワークの多くがすでにcamelCaseメソッドを採用済みだったこと
    - PHP-FIGの創設に関わった人物たちが、まさにそれらのフレームワークの開発者だったこと（次章で詳述）
- 記事での温度感の指定
  - 「会議室、もうだいぶcamelCaseの香りだった説」のようなネタは記事でも残してよいが、断定的な書き方を避け「〜かもしれません」「状況証拠としては」という言い回しに変換する
- 技術要素として追加できるもの
  - CodeIgniterがsnake_case寄りだった点についてもう少し触れる
    - CodeIgniterはPHP標準関数に近い手続き的なスタイルを好む思想があったとされる（要出典確認）

## 7. Symfony helperの余談

### 雛形
- スライドの「Symfony helperの余談」に対応
- 記事ではこのエピソードを「関数文化とOOP文化の共存」を示す最も具体的な証拠として厚めに扱う

### 書く内容（箇条書き）
- Symfony 1系での命名事情
  - 基本的にメソッドはcamelCase
  - しかしテンプレート内で使うhelper関数はunderscore（snake_case）形式
    - 例: `link_to()`, `use_helper()` のような関数（要具体例の出典確認）
- Symfony公式ドキュメントでの説明
  - 「なぜhelperだけcamelCaseじゃないのか」という疑問を公式ドキュメント自身が取り上げていた
  - その回答: helperは（メソッドではなく）関数だから、PHPのcore functionの命名文化に合わせた
- ここから読み取れること
  - 2000年代後半の時点で、同じフレームワークの中にすでに
    - 「PHP標準関数の文化（snake_case、手続き的）」
    - 「OOPフレームワークの文化（camelCase、メソッド）」
    - の2つが共存していたことを示す一次的に近い証拠になる
  - この事実は、記事の結論（関数はsnake_case、メソッドはcamelCase）の一番具体的な裏付けとして使えるので、他の章より厚めに書く価値がある
- 記事での扱い方
  - 「PSRが生まれるより前から、PHPコミュニティは “関数はsnake_case、メソッドはcamelCase” という使い分けを自然と実践していたのでは」という繋ぎの一文を入れる

## 8. PHP-FIGとPSR

### 雛形
- スライドの「2009 PHP-FIGができる」〜「その周辺の命名規則を見ると」に対応
- 記事では「公式」という言葉の扱いに注意しつつ、PHP-FIGの成り立ちを詳しめに書く

### 書く内容（箇条書き）
- PHP-FIGの基本情報
  - PHP Framework Interop Group
  - 2009年、php|tekというカンファレンスの場でフレームワーク開発者たちが集まって始まったとされる（要一次資料の確認、現時点では推測寄り）
  - 目的は相互運用性（Interoperability）: 共有されるPHPコード、フレームワーク間で混ざりやすいコード、ライブラリとして使いやすいコードを増やすこと
- 創設/初期メンバー周辺の整理（記事では「厳密な創設5名の対応表ではない」ことを明記した上で）
  - Matthew Weier O'Phinney: Zend Framework
  - Fabien Potencier: Symfony
  - Paul M. Jones: Solar / Aura
  - Jonathan Wage: Doctrine
  - Nate Abele: Lithium
  - それぞれの周辺プロジェクトのメソッド命名傾向がcamelCaseだったことを表にする
- PSRの立ち位置についての整理
  - PSRはPHP本体の言語仕様（構文・実行系）ではない
  - PHP処理系がPSRに従うことを強制するわけではない
  - しかしPHPエコシステム内では事実上の共通規格として広く参照されている、という位置づけ
  - 記事では「公式」「公認」という言葉を避け、「事実上の標準」「広く参照される共通規格」という言い回しに統一する
- 技術要素として追加できるもの
  - PSRにはPSR-1, PSR-12以外にも、autoloading（PSR-4）、ロギングインターフェース（PSR-3）、HTTPメッセージ（PSR-7）など多数存在することに軽く触れて、PHP-FIGが命名規約だけでなくエコシステム全体の相互運用性を担っている組織であることを示す（本題から逸れすぎない程度に一段落程度）

## 9. PSR-1が言うこと、言わないこと

### 雛形
- スライドの「PSR-1: Basic Coding Standard」〜「じゃあPSRはなぜ標準関数っぽくないの？」に対応
- 記事ではPSR-1原文に近い引用と出典リンクを必ずセットにする

### 書く内容（箇条書き）
- PSR-1の目的（出典: https://www.php-fig.org/psr/psr-1/）
  - 「共有されるPHPコード間で高い技術的相互運用性を確保するため」という一文をほぼそのまま引用（15語未満の直接引用ルールに注意しつつ要約中心にする）

## 10. それでも命名で悶える

### 雛形
- スライドの「PSRを知らなくてもPHPは書けます」〜「それはそれとして悶えることはあります」に対応
- 記事ではここに、PHPが動的型付け・緩い実行モデルであることの技術的背景を足して厚くする

### 書く内容（箇条書き）
- PHPの言語仕様として、命名規則は構文レベルでは何も強制されない
  - 変数名・関数名・メソッド名がsnake_caseだろうがcamelCaseだろうがPascalCaseだろうが、構文エラーにはならない
  - PSRに従わなくても普通に実行できるコードが書けてしまう、という事実
- この「書けてしまう」ことの功罪
  - 功: 初心者でも命名規則を意識せずすぐに書き始められる、PHPの学習コストの低さにつながっている
  - 罪: チームで書くコードになった途端、命名のブレがコードレビューや可読性の面で顕在化する
- 個人の経験談として（記事の一人称パート）
  - 歴史的経緯やPSRを知らずに書かれたコード（あるいは自分自身が過去に書いたコード）を読むと、命名のブレで混乱した経験があることを書く
  - 「知らなくても書けてしまう」というPHPの性質そのものが原因であり、書いた人を責める話ではない、というトーンを明記
- ここでの繋ぎ
  - だからこそ、歴史的な経緯を知った上で「自分たちのプロジェクトではどう判断するか」という実務的な指針が欲しくなる、という流れで次章（現代の実装判断）につなげる

### 書く内容（箇条書き）

  - OOPの文化
  - PSRの規定
  - プロジェクトの一貫性
  - フレームワークの規約
  - 公開APIの互換性
- 具体的な提案
  - グローバル関数・ヘルパー関数・手続き的APIは `snake_case`
    - 理由: PHP標準関数文化に寄せると、PHP標準ライブラリや他の手続き的コードとの一貫性が保ちやすい
  - クラスのメソッドは `camelCase`
    - 理由: OOP PHP文化、および現行のPSR-1の規定に沿う
  - プロパティ・変数名はスコープ内で一貫性を保つことを優先（PSR-1がここを規定していないことの裏返し）
- 既存規約を最優先するという例外条件（重要な線引きとして繰り返す）
  - 既にsnake_caseメソッドで統一されているプロジェクトなら、それに合わせる
  - Laravel, Symfony, WordPressなど、周辺エコシステムの慣習を尊重する
  - 公開APIは後方互換性を壊さないことを最優先する
- 判断フローチャート（Mermaidで表現する案）
  - 「既存規約はあるか？」→ Yes: それに従う / No: 次へ
  - 「フレームワーク規約はあるか？」→ Yes: それに従う / No: 次へ
  - 「クラスのメソッドか？」→ Yes: camelCase / No: 次へ
  - 「グローバル関数・ヘルパーか？」→ Yes: snake_case
  - 「それ以外（変数・プロパティなど）」→ スコープ内で一貫性を優先
  - 記事内では ```mermaid flowchart TD``` のコードブロックとして実装する想定（実装はarticle.md執筆時に行う）
- 記事だけで追加できる技術要素
  - 静的解析ツール（PHP_CodeSniffer, PHPStanなど）でPSR-1/PSR-12準拠を機械的にチェックできることに触れる
  - チームでの命名規則統一に、`.php-cs-fixer.php` やPHPStanのルールセットを使う実務的なTipsを1段落程度追加する（本題を食わない範囲で）

## 用語解説ブロックの方針

- スライドは口頭説明で補えるが、記事は文字だけなので「一般的な開発者なら知っている」と言い切れない単語は本文中で流さず、独立した補足ブロックで説明する
- 目安: PHP以外の言語もある程度書く開発者なら知っていそうな単語（変数、関数、クラス、メソッド、interfaceなど）は解説不要
- 判断基準
  - PHPの歴史・コミュニティ特有の固有名詞（PHP-FIG、PSR、PEAR、php|tekなど）→ 基本的に解説ブロックが必要
  - CS一般の用語でも初心者には馴染みが薄い可能性がある概念（後方互換性/BC、名前空間、ORM、静的解析など）→ 解説ブロックが必要
  - 特定の製品名・ツール名で読者が触れたことがない可能性があるもの（PHPStan、PHP_CodeSniffer、Zend Engineなど）→ 一言解説ブロードが必要
  - 迷ったら「知らなくても記事の論旨は追えるが、知っていると解像度が上がる」程度でも補足ブロックを入れる方に倒す
- 記事内での表現形式（案）
  - Markdownの引用ブロック（`>`）か、小さい見出し＋短い説明の形で本文の流れを止めずに挿入する
    ```markdown
    > **PSRとは**
    ```
