# **PRD: 目的・報酬駆動型 自律学習ロボット**

---

## **Overview / Problem Statement**

個人でホビーロボットを開発しているAさんは、これまで「指定地点まで移動する」「障害物を回避する」といった機能を実装するたびに、経路計画や回避ロジックを一つひとつ手作業で設計・コーディングしてきた。「人間を追跡する」「特定の対象を探す」のような新しいタスクを追加したいと思うたびに、既存の実装をそのまま流用できず、似たようなロジックをほぼゼロから組み直す必要がある。

* **実装コストの累積:** タスクを1つ追加するごとに、動作設計から制御ロジックの実装までを個別に行う必要があり、対応タスクが増えるほど開発・保守コストが積み上がる
* **環境変化への弱さ:** 部屋のレイアウトや障害物の配置が変わると、作り込んだロジックの前提が崩れ、細かな調整や作り直しが発生する
* **検証したい問いに対する開発基盤の不在:** Aさんは、ゲームの仮想空間で高度な自律エージェントが目的と報酬だけを与えられて複雑な行動を獲得している様子を見て、**「同様のことが現実世界のロボットでも起こせるのか」**を確かめたいが、それを検証するための開発基盤を持っていない

そこで本プロジェクトでは、ロボットに対して人間が細かな動作を実装するのではなく、**「目的」と「報酬」を与えるだけで、その目的を達成するための行動をロボット自身が学習できるシステム**を開発する。現実世界そのものを「最も高精度な物理演算環境」と捉え、シミュレーションによる大量学習と実機環境での継続学習を組み合わせ、Sim-to-Real Gapをどこまで縮められるかについても併せて検証する。最終的には、最低限の移動能力と環境認識能力だけを持ったロボットが、どこへ移動するべきか・障害物をどう回避するべきか・人間と無機物をどう区別するか・目的達成のためにどのような行動を取るべきかを、継続的な学習によって獲得することを目指す。

## **Goals / Non-Goals**

### Goals

* ロボットが自律的に移動できること
* カメラや距離センサー等を利用して周囲の環境を認識できること
* 障害物を認識し、回避行動を学習できること
* 人間と無機物をある程度区別できること
* 人間が設定した目的に対して報酬関数を設定でき、報酬を最大化するようにロボット自身が行動戦略を学習できること
* シミュレーション環境上で24時間継続して学習可能な環境を構築すること
* シミュレーション上で獲得した行動を実機へ転移し、実機環境のセンサー情報を利用して追加学習・調整できること
* ロボット本体を交換しても、一定の範囲で学習システムを再利用できること

初期の代表的な検証タスクとして、指定地点への移動・障害物回避・人間の認識・人間の追跡・「かくれんぼの鬼」として人間を探索/追跡する、の5つを想定する。最終的には、ハードウェアが物理的に実行可能な範囲であれば新しい目的を与えることで新しい行動を獲得できる状態を目指す。

### Non-Goals

* 人間への危害を目的とした機能の開発
* 武器や攻撃装置の搭載
* 許可を得ていない場所・公道での屋外自律走行
* ロボットハードウェアそのもののゼロからの開発
* 特定のロボット専用の制御システムの構築
* 初期段階から完全な汎用人工知能を実現すること
* すべての行動を完全なEnd-to-End学習のみで実現すること

安全性や開発効率の観点から、ロボット本体については既存製品・開発キット・プログラム制御可能なロボットを利用し、必要に応じてカメラ・距離センサー・IMU等を追加する。非常停止・速度制限・衝突防止などの安全機構は、学習AIとは独立した制御層として実装する。

## **Proposed Solution / Feature Description**

**Simulation → Training → Model Transfer → Real World Fine-Tuning** という構成を基本とする学習システムを提供する。学習・推論(行動決定)は原則すべてサーバー側で行い、**ロボット本体はセンサー情報のサーバーへの送信と、サーバーから指示された処理(モーター駆動等)の実行のみを担う**構成とする。ロボット本体を薄いクライアントとして扱うことで、モデル差し替えや複数ロボットへの展開を学習システム側の変更だけで完結させる。ロボット・サーバー間の具体的な通信方式(プロトコル、帯域、切断時の扱い等)は別途検討する。

主要な構成要素:

1. **Robot Client** — Motor / Camera / Distance Sensor / IMU / Encoder / Battery 等を共通インターフェースとして扱い、センサー値の送信とサーバーからの指示(行動コマンド)の実行のみを行う。学習・推論ロジックは持たない
2. **Robot-Server Communication Layer** — センサー情報のアップリンクと行動コマンドのダウンリンクを担う。具体的な通信方式・プロトコルは別途検討するが、遅延・切断が発生しうる前提でシステム全体を設計する
3. **Server-Side Simulation Environment** — 実機に近いロボットモデルをサーバー上のシミュレーションで構築し、移動・旋回・停止・障害物回避・目的地点への接近などの基本行動を高速かつ24時間継続で学習する
4. **Basic Policy Training** — 完全なランダム行動からの学習は試行回数が膨大になりうるため、人間の操作データ・既存の単純な制御アルゴリズム・Curriculum Learningを用いて最低限の行動を先に獲得させる(ゼロからの学習も比較実験の対象とする)
5. **Reinforcement Learning** — 目的達成のための主要な学習方法とする。例えば「指定地点への移動」であれば、目的地点への接近・到達・無衝突移動をPositive Reward、障害物への衝突・目的地からの後退・停滞をNegative Rewardとする
6. **Perception** — 既存のVision Model等も活用しつつ、人間・無機物・障害物・移動可能領域を最低限識別できる状態を目指す。推論はサーバー側で実行し、ロボットはカメラ映像等の生データを送信するのみとする
7. **Sim-to-Real Transfer** — 摩擦・モーター出力差・センサーノイズ・通信遅延などシミュレーションで再現しきれない要素に対し、Domain Randomizationで学習した上で実機Fine-Tuningを行う。サーバー推論を前提とするため、通信遅延そのものもランダム化対象に含める
8. **Continuous Learning** — 学習済みモデルを固定せず、実機評価で得た経験を再学習に組み込み、モデルバージョンを継続的に更新する。モデル更新はサーバー側のみで完結し、ロボット本体への再デプロイを必要としない
9. **Safety Layer** — ロボット本体側にSafety Controllerをローカルに配置し、速度制限・加速度制限・衝突防止・非常停止・行動範囲制限を、サーバーとの通信状態(遅延・切断)に依存せず適用する

代表的な統合検証タスクとして、「対象となる人間を発見し、一定距離まで近づく」ことを目的としたAI Robot Hide-and-Seek Demoを実施する。安全上、接触そのものは成功条件とせず、一定距離以内への到達を成功条件とする。

### (High-Level Tech Consideration)

* **Simulation:** NVIDIA Isaac Sim / Isaac Lab、MuJoCo、Gazebo。大量の並列シミュレーションが可能な環境を優先する
* **Machine Learning:** Reinforcement Learning(PPO / SACから開始)、Imitation Learning、Curriculum Learning、Domain Randomization。完全なランダム初期Policyだけでなく、人間操作デモデータを利用した初期学習も比較する
* **Perception:** Object Detection、Person Detection、Depth Estimation、Visual Tracking。既存モデルを積極的に利用し、ロボット固有の学習にリソースを集中する
* **Compute:** 学習・推論用のGPUはすべてサーバー側(ローカルGPU / GPU Workstation / Cloud GPU)に集約する。ロボット本体側は通信処理と指示実行に必要な最低限の計算資源のみを搭載し、GPU購入費用・クラウド利用料金・電気代の総コストが合理的な方式を選択する
* **Robot Hardware:** プログラムから移動・センサー取得・外部制御が可能で、カメラ等を追加でき、室内で安全に実験でき、消耗部品を交換できる既存ロボットを選定する(自作は行わない)。ロボット側にAIモデルを持たせない前提のため、要求スペックは通信・センサー入出力・指示実行に限定して選定できる
* **Robot-Server Communication:** プロトコル・帯域・遅延要件・切断時の挙動は別途検討する。少なくともセンサーデータのアップリンクと行動コマンドのダウンリンクを継続的に行える方式であることを前提とする
* **Safety Layer:** AI Policy(サーバー側) → 通信 → Safety Controller(ロボット本体側にローカル配置。Speed Limit / Acceleration Limit / Collision Prevention / Emergency Stop / Operating Area Limit) → Robotという構成とし、通信遅延・切断時でも安全機構が独立して機能するようにする

## **User Stories**

### **US-001 目的と報酬だけによる行動学習**

開発者は、ロボットに新しい目的(例:「この地点まで移動する」)と報酬条件(例:「目的地点に近づくほど高い報酬を与える」)だけを設定し、移動方法そのものはAIに獲得させたい。それにより、タスクごとに動作や制御ロジックを個別実装するコストをなくせる。

**背景:** 現状の多くのロボットシステムはタスクごとに人間が制御ロジックを設計する必要があり、新しい目的の追加コストが高い。

### **US-002 学習状況のモニタリング**

開発者は、ロボットがどのような学習過程を経ているのかをEpisode数・累積報酬・成功率・学習時間・移動距離・衝突回数・モデルバージョンなどで確認したい。それにより、学習が意図通り進んでいるか、モデルの改善が進んでいるかを判断できる。

**背景:** 学習は長時間・大量試行にわたるため、結果だけでなく途中経過を可視化できないと異常や停滞に気づけない。

### **US-003 複数学習方式の比較**

研究者は、どの学習方法が実世界で動くロボットに最も適しているかを検証するため、複数の学習方式(完全ゼロスタート/事前学習あり、RLアルゴリズムの違い等)を比較したい。それにより、学習速度・性能・計算コストのバランスに優れた方式を選定できる。

**背景:** 本プロジェクトの中心的な問いは、ゲーム内AIに近い自律性が現実世界でどこまで成立するかであり、単一の学習方式だけでは十分な検証にならない。

### **US-004 人物探索タスクの目的設定**

操作者は、ロボットに「この人を探す」という目的を設定し、ロボットが環境内を探索しながら対象を発見できるようにしたい。それにより、探索・発見のための動作を個別に実装せずに応用タスクを試せる。

**背景:** Hide-and-Seek Demoをはじめとする応用タスクの多くは、探索・発見という共通の能力を必要とする。

### **US-005 安全な人物追跡**

操作者は、人間が移動した際に、ロボットが安全な範囲でその人を追跡できるようにしたい。それにより、対象の位置が変化する状況でも目的を継続的に達成できる。

**背景:** 追跡対象は静止しないため、発見後も継続的な再探索・追従が必要であり、かつ接触は安全上避ける必要がある。

### **US-006 将来的な現場適用(災害時・避難所等)**

利用者は、将来的に人間が常に操作できない環境(災害時や避難所など)においても、ロボットへ目的だけを与えることで必要な行動(巡回・物資の探索・対象の探索・室内探索等)を自律的に選択できるようにしたい。

**背景:** 本プロジェクトが目指す「目的だけを与えれば行動を獲得できる」性質は、個別実装が追いつかない緊急環境でこそ価値を持つ。

## **Open Questions / Risks**

* 初期学習問題:移動すらできない状態からは意味のある報酬を得られず学習が進まない可能性がある(Imitation Learning / Human Demonstration / Curriculum Learning / Reward Shapingで対策を検討)
* Sim-to-Real Gap:シミュレーションで学習した行動が実機で成立しない可能性がある(Domain Randomization、センサーノイズ・摩擦・モーター出力のランダム化、実機Fine-Tuningで対策)
* Hardware Damage:実機学習中の衝突・転倒による破損リスク(Safety Controller・速度制限・実験区域制限で低減)
* Compute Cost:24時間継続学習に必要なGPU資源のコスト(クラウド利用料金 vs ローカル購入費用+電気代を初期にBenchmarkして見積もる)
* Reward Hacking:AIが意図しない方法で報酬の抜け道を利用する可能性(本プロジェクトの研究対象としても扱う)
* Catastrophic Forgetting:新しいタスクの学習によって既存能力を失う可能性(複数タスクの経験を保持した継続学習の方法を検討)
* Generalization:特定の部屋・障害物配置にのみ適合したPolicyになる可能性(環境・障害物・照明・スタート位置のランダム化で対策)
* Hardware Dependency:ロボット本体の性能が学習可能な行動範囲を制限すること自体は前提とし、その範囲内での目的達成能力の獲得を目標とする
* Communication Design:ロボット・サーバー間の通信方式(プロトコル、必要帯域、許容遅延、切断時のフォールバック動作)が未定であり、サーバー推論を前提とする本構成の実現性を左右する
* Latency Impact:サーバー推論の往復遅延が、障害物回避や人物追跡など即応性が求められるタスクの成立可否にどこまで影響するか
* プロジェクト初期に選定すべき項目:ロボット本体、センサー構成、シミュレーション環境、RLアルゴリズム、Safety設計、ロボット・サーバー間通信方式の具体案
