## 主張の線引き

PSRが言っていること

- クラス名は `StudlyCaps`
- クラス定数は `UPPER_CASE_WITH_UNDERSCORES`
- メソッド名は `camelCase`
- プロパティ名は特定の規則を推奨せず、一貫性を求める

PSRが言っていないこと

- 普通の関数名を `camelCase` にせよ、とは言っていない
- 変数名を `camelCase` にせよ、とはPSR-1/PSR-12の中心主張ではない
- PSRはPHP処理系が強制する言語仕様ではない

この発表での提案

- グローバル関数、ヘルパー関数、手続き的APIは `snake_case` が自然
- クラスのメソッドは `camelCase` が自然
- 既存プロジェクト規約、フレームワーク規約、公開APIの互換性はこの提案より優先

### 10. 現代の判断

#### 52. 普通の関数はsnake_case

- 対象: グローバル関数、ヘルパー関数、手続き的API
- 理由: PHP標準関数文化に寄せると自然
- 注意: PSRがそう定めているわけではない
- 役割: 結論1

#### 53. メソッドはcamelCase

- 対象: クラスのメソッド
- 理由: OOP PHP文化と、その時点の最新規格に沿う
- 役割: 結論2

#### 54. でも既存規約が最優先

- 既に `snake_case` メソッドで統一されているなら合わせる
- Laravel、Symfony、WordPressなどの周辺文化を尊重する
- 公開APIは互換性を壊さない
- 役割: 現実的な例外

#### 55. 判断フローチャート

- 既存規約がある? → 従う
- フレームワーク規約がある? → 従う
- クラスのメソッド? → `camelCase`
- グローバル関数/ヘルパー? → `snake_case`
- それ以外? → スコープ内で一貫させる
- 役割: 明日から使える形に落とす

### 2. 先に結論

- 普通の関数は `snake_case`
- メソッドは `camelCase`
- ただし絶対ルールではない
- 既存規約、フレームワーク規約、公開APIの互換性を優先

### 3. PHP標準関数はなぜsnake_caseっぽく見えるのか

書く内容

- 初期PHPはRasmus Lerdorf氏のPersonal Home Page Toolsから始まった
- もともとはCで書かれたCGIバイナリ群
- 個人用ツールから始まり、要求に応じて機能が増えた
- 標準関数には `str_replace`, `array_map`, `json_encode`, `file_get_contents` など `snake_case` が多く見られる
- ただし完全統一ではない
- 標準機能にも `camelCase` はあるが、例として出すならグローバル関数ではなく標準クラスのメソッド側として扱う
  - `ReflectionClass::getName()`
  - `ReflectionMethod::getParameters()`
  - `DateTime::setTimezone()`

記事で補足するポイント

- 「言語設計がなかった」と断言しすぎない
- 「最初から30年後の巨大エコシステムを想定してAPI命名を整えていたわけではない」くらいの表現が安全
- PHP公式マニュアルの命名ルールでは、procedural function names は lowercase + underscore とされ、クラス名は camelCase / PascalCase 系も使われると説明されている
- つまり「標準にcamelCaseがない」ではなく、「グローバル関数の文化と標準クラス/メソッドの文化は分けて見る」が安全

### 4. PHP 3で広がる関数ベースのWeb言語

書く内容

- PHP 3はPHP/FIからPHPへ移る大きな節目
- 開発チームやモジュールが広がる
- 機能拡張と実用が先にあり、命名の一貫性だけが主目的ではなかった

記事で補足するポイント

- 「誰が、いつ、どの文化圏からAPIを追加したか」で命名は変わる
- 一度広がった関数名は互換性のため簡単に変えられない

### 5. PSR以前のPEAR規約

書く内容

- PSR以前にもPEARのコーディング規約があった

- メソッドはcamel系
- 定数はアッパースネーク
- グローバル関数もPEAR規約ではcamel系を推奨していた点は、発表の結論と切り分ける

記事で補足するポイント

- ここで「PHPの歴史は単純ではない」と示す
- 「普通の関数はsnake_case」という結論はPEAR規約からではなく、PHP標準関数文化や現在の文脈からの判断

### 6. PHP 5でOOP PHPが強くなる

書く内容

### 7. 2000年代後半のフレームワーク文化

## 事実確認メモ

### PSR-1

出典: https://www.php-fig.org/psr/psr-1/

- PSR-1の目的は、共有されるPHPコード間の高い技術的相互運用性
- クラス名は `StudlyCaps`
- クラス定数は大文字とアンダースコア
- メソッド名は `camelCase`
- プロパティ名については `$StudlyCaps`, `$camelCase`, `$under_score` の推奨を意図的に避け、一貫性を求める

### PHPの歴史

出典: https://www.php.net/history.php.php

- PHPはPHP/FIの後継
- 最初期はRasmus Lerdorf氏によるCで書かれたCGIバイナリ群
- Personal Home Page Toolsとしてオンライン履歴書の訪問者追跡に使われた
- 1995年6月にPHP Toolsのソースコードが公開された
- PHP 3.0は1998年6月に公式後継として発表
- PHP 5は2004年7月にリリースされ、Zend Engine 2.0と新しいオブジェクトモデルを持つ

### PEAR命名規約

出典: https://pear.php.net/manual/en/standards.naming.php

- PEARのクラス名は先頭大文字
- クラス階層をアンダースコアで表現する
- 例: `Log`, `Net_Finger`, `HTML_Upload_Error`
- クラス変数とメソッドはstudly caps / camel caps
- 例: `$counter`, `connect()`, `getData()`, `buildSomeWidget()`
- 定数は大文字とアンダースコア

### PHP公式の命名ルール

出典: https://www.php.net/manual/en/userlandnaming.rules.php

- PHPは新しい内部識別子を選ぶときの権利を予約している
- 関数名は単語間にアンダースコアを使う
- クラス名は `camelCase` と `PascalCase` の両方のルールを使う
- 過去には例外も多くある
- `strpos()` は過去のミスの例として挙げられている
- `DOMDocument`, `SplFileObject` のように標準クラス側にはcamel/Pascal系の名前がある
